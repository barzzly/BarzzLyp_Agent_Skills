# Dungeon worlds and WorldGuard scope

1. Inspect dungeon mode and world binding in source plus runtime config before advising flags. PRIVATE instance worlds are temporary, plugin-managed copies; PUBLIC dungeons use an already-loaded, persistent world. Isolation hooks keyed to managed instance names do not bypass WorldGuard in PUBLIC worlds.
2. Resolve the exact world name used by the PUBLIC arena and inspect its WorldGuard `__global__` region plus overlapping regions at the affected coordinates. Do not assume a global flag wins over higher-priority region flags.
3. For MMO abilities, identify the owning plugin first. MythicLib documents the WorldGuard state flag as `mmo-abilities` (`MMO_ABILITIES` in its compatibility table); `DENY` blocks MMOItems/MMOCore skills when `plugins/MythicLib/config.yml` has `enable_flag_checks.skills: true`. This does not automatically disable AuraSkills or MythicMobs abilities. Check loaded plugin list and MythicLib's live config before claiming the flag works.
4. For an authorized PUBLIC-world change, target the actual persistent world, not a PRIVATE instance: from console run `rg info -w <world> __global__`, then `rg flag __global__ mmo-abilities -w <world> deny`. Read server log for WorldGuard's confirmation (`Region flag mmo-abilities set ... DENY`), run `rg save -w <world>`, and read back `rg info -w <world> __global__`. A Pterodactyl command HTTP 204 means queued, not proof of execution; confirm from console/log. Do not restart server for a region flag change. Check higher-priority overlapping regions before promising behavior across the entire dungeon; gameplay needs a player skill test.
5. If asked only whether the arrangement works, answer the scope question without changing flags, plugin config, or server state.
