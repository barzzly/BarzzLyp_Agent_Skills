# RedstoneLimiter config cross-server copying

- User may explicitly authorize config-only copying from LegacySchool to Noesantara even though cross-server plugin JAR copying remains prohibited. Inspect both live `plugins/RedstoneLimiter/config.yml` and JAR SHA-256/plugin.yml first; require compatible plugin version. Compare semantics and behavioral impact (period, thresholds, piston push) rather than assuming friend's config fixes redstone.
- Back up exact source and destination config locally, validate YAML shapes, compare destination bytes immediately before writing; upload source config unchanged and read back exact bytes. Check the plugin is active in the **current boot** before issuing `/redstonelimiter reload`; a JAR/config folder or earlier successful command does not prove current activation. Require log `Configuration reloaded.` plus fresh `/redstonelimiter perblock` period matching source. HTTP 204 means queued, not executed. Never restart the whole server just to claim a plugin reload succeeded.
- Copying stricter limits can increase blockage: compare period, thresholds, and `max_piston_push` before reporting impact. Compare blocked counters during the affected player's test, not only unrelated global totals; obtain in-world confirmation before claiming gameplay success.
- For a rollback, locate the exact pre-copy destination backup, compare live bytes to the copied source before overwriting (stop on divergence), write original bytes, and read them back. Then reload **only if the plugin is active**, verify reload in the current log and in-memory settings; if inactive, report disk restored but runtime reload unavailable, without a server restart.
