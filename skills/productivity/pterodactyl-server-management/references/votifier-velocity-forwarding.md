# VotifierPlus Velocity forwarding

- Trace real vote records through proxy and backend before editing. A proxy receiving votes with `serverGreeting is null` can still forward to an obsolete backend after migration. Check configured destination against current allocated Votifier port, receive greeting with a read-only socket probe, and compare token privately. Do not print tokens or player addresses.
- Back up `/plugins/votifierplus/bungeeconfig.yml`; change only `Forwarding.<name>.Host` and `.Port` to verified backend allocation. Preserve listener, RSA keys, token and enabled state. Read back exact config before reload.
- Inspect installed JAR command parser. VotifierPlus 1.4.3 Velocity registers `votifierplusbungee` with aliases `votifierplus` and `votifierplusvelocity`; native reload is `votifierplusvelocity reload`.
- This build's reload updates shared Config and tokens but calls `loadVoteReceiver()` without shutting down old listener. It may emit `java.net.BindException: Address already in use`. Do not repeat reload, use whole-server reload, regenerate keys or restart server against user's restriction. Original listener can remain active; its callback reads current shared Config for every forwarded vote. Verify greeting and a NEW real vote at both proxy and backend rather than treating reload text or bind error alone as success/failure.
- Verify backend VotifierPlus received record and VotingPlugin processed corresponding service/name/time. Receiving/processing a vote does not prove individual reward delivery; inspect user storage/provider receipt or ask user for reward confirmation. Never replay old votes or send synthetic votes to real players without explicit authorization; rewards and counters can duplicate.
- Avoid naming scripts `inspect.py`, `socket.py` or other stdlib modules: they shadow dependencies when local cwd is on sys.path and can trigger misleading Paramiko circular import errors.
