# Safe plugin player-data resets

1. Confirm all players versus named UUIDs and exact database token. Read live plugin SQL config and panel database inventory; assert the configured database matches before connecting. Never infer scope from a similar database name. Preserve separate Coin storage and unrelated class/quest receipts.
2. Discover tables, columns, storage engines and foreign keys through information_schema. Record row counts and migration contents before changes. Distinguish player tables from schema migrations, audit logs and global metadata; do not blanket-truncate the schema.
3. Confirm interruption timing when players are online. Inspect active dungeon runs and Chunky tasks. Stop every writer using the database and verify offline before backup/reset; cached player data can otherwise recreate deleted progress. Honor the latest requested final power state rather than automatically restarting.
4. Create a private full SQL backup after shutdown using `mariadb-dump --defaults-extra-file=<private-client.cnf> --single-transaction --quick --hex-blob --skip-lock-tables <database>`. Put credentials in a mode-0600 option file, not command arguments. Check exit status, expected CREATE TABLE statements, completion marker, size and SHA-256. These checks establish a completed dump, not a tested restore; do not claim restore verification without exercising it separately.
5. For the inspected AuraSkills schema, reset `auraskills_skill_levels`, `auraskills_key_values`, and `auraskills_modifiers` before `auraskills_users`. With InnoDB, prefer child-first DELETE statements inside START TRANSACTION/COMMIT; this preserves foreign-key enforcement and permits rollback, unlike TRUNCATE's implicit commits. Filter player-associated `auraskills_logs` by nonempty player_uuid if those logs are in the approved scope; preserve global logs. Re-discover schema before applying these names to another version.
6. Preserve `auraskills_schema_migrations` exactly. Removing migration history while tables remain can rerun CREATE TABLE migrations and break startup. Do not reset AUTO_INCREMENT merely to make the database look new.
7. Read counts through fresh queries after commit: require zero for every approved player-data table/filter, unchanged migration rows and requested server power state. Record before/after counts and backup path in a private verification manifest. Remove temporary credential files after checks.
8. If startup was authorized, verify fresh AuraSkills initialization separately and expect new default player rows on joins. If only stopping/resetting was requested, leave offline and report that explicitly. Deleting AuraSkills DB rows does not automatically revoke historical permission rewards or alter external plugin data; do not claim a whole-network character wipe.
