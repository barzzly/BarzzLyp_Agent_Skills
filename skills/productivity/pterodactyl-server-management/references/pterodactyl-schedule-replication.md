# Pterodactyl Schedule Replication & Management

- Fetch source schedules via Client API `GET /api/client/servers/{source_id}/schedules`. Extract target schedule attributes (`name`, `is_active`, `cron` mapping minute/hour/day_of_month/month/day_of_week, and `only_when_online`).
- Create schedule on target server via `POST /api/client/servers/{target_id}/schedules` with the extracted cron and online gating payload. Retrieve generated target schedule ID.
- Replicate all child tasks from source `relationships.tasks.data` in sequence order via `POST /api/client/servers/{target_id}/schedules/{schedule_id}/tasks`:
  - Preserve `action` (`command` or `power`), exact multiline `payload`, integer `time_offset`, and `continue_on_failure`.
- Read back target schedule and task collection via `GET /api/client/servers/{target_id}/schedules/{schedule_id}`; assert identical task counts, sequence order, actions, offsets, and payloads.
- Console command syntax caution in scheduled tasks: in modern Paper/Purpur (1.20+), gamerule or world-scoped queries executed from console must specify dimension context (e.g., `execute in minecraft:overworld run gamerule minecraft:random_tick_speed`), as unqualified legacy commands fail argument validation.
- Scheduled restart task action pitfall: server restarts in Pterodactyl schedules must use `action: "power"` with `payload: "restart"`, never `action: "command"` with `payload: "restart"`. The in-game/console `restart` command invokes Spigot's `RestartCommand` which looks for `./start.sh` (configured in `spigot.yml`). Since container environments lack `./start.sh`, Spigot terminates with `Startup script './start.sh' does not exist! Stopping server.` and leaves the server offline indefinitely.
- Cron timing & timezone: Pterodactyl schedules execute in UTC. When targeting regional times like WIB (UTC+7), offset by -7 hours (e.g., 22:00 WIB target restart with 10m broadcast warning requires `hour: "14"`, `minute: "50"`). Never use `minute: "*"` for scheduled restarts, as it triggers every minute throughout the specified hour.
- Some Client API tokens permit schedule creation and editing but return HTTP 403 on `DELETE /schedules/{id}`. For replacement, verify new schedule active and all tasks before attempting deletion; if deletion is denied, keep old schedule explicitly inactive and disclose leftover to user. Never turn the old unsafe restart schedule back on.
- Database container restart synchronization: When an application/game server (e.g. Paper Minecraft) relies on an external or containerized MariaDB database container on the same panel, do not restart the database during active gameplay or simultaneously with the game server start time. Set a dedicated schedule on the database container matching the game server's restart hour with a 20-second offset (e.g., if Minecraft restarts at 03:00 UTC with countdowns starting at 02:50, schedule the DB restart task for 03:00:20 UTC). This allows the Minecraft server to save all player data and close connection pools cleanly before MariaDB reboots, and guarantees MariaDB finishes its restart cycle (~3 seconds) before the Minecraft server finishes booting and attempts reconnection.
- Pterodactyl Client API file rename method: Renaming files via Pterodactyl Client API requires `PUT /api/client/servers/{server_id}/files/rename` with payload `{"root": "/path", "files": [{"from": "old_name", "to": "new_name"}]}`. Using `POST` returns HTTP 405 Method Not Allowed.
