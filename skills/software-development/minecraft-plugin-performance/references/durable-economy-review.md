# Durable economy release boundaries

- Treat Vault SUCCESS as synchronous API return, not provider persistence. Commit external wallet only from provider-owned receipt bound to operation/player/kind/amount and exact before/after, persisted atomically with balance; fsync bridge journal alone cannot establish this.
- Share authoritative money/receipt state across every User instance for same canonical account path. Cache expiry and public User construction can leave old instances alive; one global writer only orders stale overwrite, it does not prevent it. Test direct configurations loaded before managed ownership and recheck their generation at adoption and write; a stale writer must reject without poisoning the current owner. Never hold the global ownership monitor across fsync/move, because unrelated main-thread admissions would wait for disk.
- Synchronize balance-plus-receipt publication with every ordinary holder serializer. Async mail/settings saves can snapshot between balance change and receipt insertion even when all money mutations run on main thread.
- Reject spending/reading uncommitted transfer funds without blocking main thread. Pending provider credit must not fund other operations before durable completion; arbitrary shop item delivery remains outside economy transaction atomicity.
- Preserve storage poison across object eviction and GC. Weak per-account caches must not reload stale disk and clear an unresolved money failure. Bound any strong poison registry and fail closed at capacity.
- Keep IO admission bounded and coalesce ordinary dirty saves; do not enqueue a forced full snapshot for every setter. Time setter admission, full snapshot serialization/copy, and durable completion separately at receipt capacity; a timer ending before deferred capture cannot establish tick latency. Require every producer sharing bounded capacity to participate in reservation; checking remaining queue capacity does not reserve space for accepted dirty work.
- Distinguish pre-admission overload from uncertain disk failure. If ordinary void setters mutate before queue submission, a bounded queue cannot safely drop/reject afterward; redesign pre-mutation admission or bounded retained dirty ownership. Do not turn normal cross-account bursts into permanent storage poison or hide the issue by raising queue size.
- Validate loaded receipt keys, values, count, byte/decimal bounds and exact deltas before economy use. Reject exponent/invalid lexical forms before BigDecimal arithmetic; short exponent strings can demand huge intermediate work. Apply matching producer/recovery sign and scale rules so an acknowledged receipt remains reloadable. Validate each historical receipt independently; its after-balance need not equal current balance after later legitimate operations.
- Test non-money setters inside durable balance-event callbacks; money reentrancy guards alone do not prevent a nickname/mail save from creating a stranded ordinary completion or permit. Preserve that save's ownership through durable publication and failure.
- Test actual User reload immediately after accepted deferred mutation; skipping disk load is insufficient if the caller then reconstructs its holder from a stale configuration node. Retain dirty holder until its save completes.
- Test transaction pause across scheduler ticks and shutdown without future ticks. Skip and rotate open transactions during ordinary capture, but explicitly drain accepted offline dirty owners during shutdown.
- Bound provider-created pending lookup/duplicate future views, including repeated caller cancellation; cancelling a returned view need not detach its callback from the internal completion. Keep original persistence independent of caller completion/cancellation.
- Drain real MockBukkit async joins before fixture teardown, with a bounded timeout and unchanged exception propagation. For MockBukkit 4.76.1, avoid waiting under its synchronized task-map while join workers schedule tasks: scheduler/task-map lock inversion can deadlock. Advance ticks and wait for worker activity outside those locks; keep unmock failures visible.
- Test actual plugin disable with poisoned accounts and stalled storage, not only executor helpers. Per-user cleanup must not throw past final shutdown or block indefinitely before bounded drain begins.
- Hold one atomically retrieved cache-only user reference; isCached followed by getUser can race soft-cache eviction and trigger synchronous disk load.
- Fence writer lifecycle admission and complete dropped futures exceptionally. Never start replacement writer while shut-down writer can still replace same files.
- Test cross-process file exclusion after a rejected same-JVM duplicate opener. Closing a second descriptor after OverlappingFileLockException can release process-associated POSIX locks while the original Java FileLock still appears held; reserve same-process canonical ownership before opening another channel.
- Preserve acknowledged terminal state on exact duplicate success. Reconstructing an identical receipt with acked=false reblocks players and triggers redundant settlement even when backend idempotence prevents duplicate credits.
- Recover through non-mutating receipt lookup, never replay balance mutation to discover outcome. Missing receipt or exception means UNKNOWN unless provider also persists a terminal no-execution fence. Never refund ambiguous withdrawal automatically.
- Derive displayed result floor from exact receipt BigDecimal, not intermediate double. Large fractional values can round across integer boundary before flooring. Align bounded decimal grammar/scale across provider, bridge and backend before admitting mutation.
- Publish one versioned protocol contract before parallel workers: capability token, precise tuple, receipt type, scale, expiry and unknown semantics. Revalidate capability under transaction locks; middleware check can become stale while queued.
- Test fresh schema and additive upgrade preserving existing accounts/balances. CREATE TABLE IF NOT EXISTS does not add receipt/capability columns to deployed tables.
- Build web snapshots in staging when live app serves project dist. Standard build scripts can delete/rewrite active frontend files even without process restart.
- Keep test layers explicit: mock entrypoint, real Paper plus TLS protocol fixture, actual Express/MariaDB, and deployment are distinct. Replay captured real provider receipt into isolated backend to verify serialization contract; fabricated fixtures are not cross-system evidence.
- Freeze release criteria around the requested durability guarantee before assigning implementation. Distinguish new regressions from upstream limits: safe two-account admission for ordinary payment is not atomic two-file crash persistence. Document trusted-filesystem/single-process assumptions instead of silently expanding single-account receipt work into arbitrary-plugin or hardware-failure guarantees; still test every in-scope public mutation path.
- Stage runtime caches and dependencies as private copies, not writable symlinks into live/project trees; pin inputs and loaded provider bytes. Exercise harness setup/selfchecks separately, then run named acceptance cases against the frozen provider. A compiled probe or successful setup is not evidence that Paper transactions ran.
- Reproduce receiver rejection before changing payment code; reserve both accounts and validate callback-edited deltas before publishing either balance, because debiting first leaves partial payment when receiver admission fails. Test one-slot capacity and listener reentrancy as well as normal payment.
- Verify exact money survives full serialization/reload, not only receipt parsing; generic BigDecimal serializers may apply MathContext rounding. Match lexical bounds on write and recovery before expensive arithmetic.
